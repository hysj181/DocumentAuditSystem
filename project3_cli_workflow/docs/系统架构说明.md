# 系统架构说明

## 1. 总体架构

系统由三个独立子项目组成：

```text
project3_cli_workflow
  ├── 子进程调用 project1_extraction
  ├── 子进程调用 project2_word_audit
  └── 读取两者真实输出，生成最终交付
```

项目三不导入项目一、项目二的内部模块，也不修改两个项目的源码和配置。

## 2. 三个项目的调用关系

```text
project3 CLI
  -> 输入解析 / SHA-256
  -> 任务指纹
  -> project1 extract 子进程
       -> project1 batch.json
  -> batch.json 校验
  -> project2 audit 子进程
       -> audit_report JSON / Markdown
       -> annotation_report
       -> math_validation
       -> annotated Word/PDF
  -> delivery
       -> 审核报告汇总
       -> 运行摘要
       -> 交付清单
       -> 批注文件副本
```

## 3. 数据流

```text
用户输入文件
  -> manifest.inputs（绝对路径、大小、修改时间、SHA-256）
  -> project1 batch.json
  -> project2 audit_report_<batch_id>.json
  -> project3 manifest 审核字段
  -> project3 03_delivery 交付文件
```

项目三不重新计算项目二的审核问题数量，所有计数来自项目二报告：

```text
metadata.pipeline.counts
metadata.pipeline.typo_counts
```

## 4. 子进程调用机制

项目一：

```powershell
<project1>\.venv\Scripts\python.exe <project1>\main.py extract `
  --input "<文件1>" `
  --input "<文件2>" `
  --mode local_gpu `
  --output-root "<任务目录>\01_extraction" `
  --save-format json `
  --quiet
```

项目二：

```powershell
<project2>\.venv\Scripts\python.exe <project2>\main.py audit `
  --batch-json "<任务目录>\01_extraction\batches\<batch_id>\batch.json" `
  --output-dir "<任务目录>\02_audit"
```

实现要点：

- 使用 `subprocess.run`。
- `shell=False`。
- 使用绝对路径。
- cwd 分别为项目一、项目二根目录。
- 捕获 stdout、stderr、退出码和耗时。
- 设置 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`。
- 日志写入任务目录 `04_logs/`。
- API Token 从日志和错误信息中脱敏。

## 6. 指纹设计

任务指纹由以下非敏感内容计算：

```text
fingerprint_version
workflow_version
manifest_schema_version
input_count
inputs（绝对路径、SHA-256、大小）
mode
project1_root
project1_python
project1_version
project2_root
project2_python
project2_version
```

实现：

1. 输入按规范绝对路径稳定排序。
2. 使用 `json.dumps(sort_keys=True, separators=(",", ":"))`。
3. 使用 SHA-256 生成 `task_fingerprint`。

安全规则：

- 不包含 API Token。
- 不包含 Token 派生值。
- 项目版本从各自 `pyproject.toml` 读取。
- 无法读取版本时禁止安全复用。

## 7. 阶段复用机制

### 提取复用

必须满足：

- 提取状态为 success 或 partial。
- batch.json 存在且属于当前任务。
- batch.json 通过完整结构校验。
- batch_id、document_count 一致。
- batch.json SHA-256 与 manifest 一致。
- 输入路径、数量和 SHA-256 与当前输入一致。
- 提取模式一致。

### 审核复用

必须满足：

- 审核状态为 success 或 partial。
- audit_report JSON 存在且 SHA-256 一致。
- report_id 非空。
- batch_id 与当前批次一致。
- pipeline、counts、typo_counts 有效。
- Markdown、批注报告、数学校验报告存在。
- 报告声明的批注文件存在。
- 审核依赖的 batch.json SHA-256 未变化。

### 交付复用

必须满足：

- delivery_status 为 delivery_success。
- 交付清单存在且可解析。
- 所有 artifact 存在。
- artifact 大小和 SHA-256 一致。
- overall_status 与 manifest 一致。
- 交付报告 batch_id、report_id、overall_status 与源报告一致。

## 8. 断点恢复机制

`resume` 流程：

```text
job_id -> manifest
  -> 重新计算输入 SHA-256
  -> 重算任务指纹
  -> 与 manifest 指纹比较
  -> 校验提取
  -> 校验审核
  -> 校验交付
  -> 从第一个无效阶段继续
```

如果输入或配置变化，拒绝恢复旧任务，避免错误复用。

## 9. 文件锁机制

任务锁文件：

```text
<任务目录>/.task.lock
```

内容：

```text
job_id
lock_id
pid
host
created_at
```

实现：

- `os.O_CREAT | os.O_EXCL` 原子创建。
- 活跃 PID 的锁不会被抢占。
- 超过 24 小时或 PID 已退出视为过期。
- 释放时只删除 lock_id 匹配的锁。
- 无法解析且较新的锁不直接删除。

限制：

- 单机文件锁，不是分布式锁。
- 两个进程同时首次运行相同输入且尚无任务时，可能各自创建任务。
- 网络文件系统的原子性取决于底层实现。

## 10. 错误分类与状态转换

任务整体状态：

```text
initialized -> running -> success / partial / failed
```

退出码：

```text
0 成功
2 用户输入错误
3 部分完成
4 外部阶段失败
5 内部错误或锁冲突
```

失败分类：

- 输入不存在、扩展名不支持、空文件夹：退出码 2。
- 项目一或项目二子进程失败、报告无效：退出码 4。
- manifest 写入失败、锁冲突、内部异常：退出码 5。
- 提取或审核部分成功、交付缺失：退出码 3。

## 11. 安全边界

- 原始 Word/PDF 只读。
- 项目一、项目二源码、配置、测试不修改。
- 项目一只向任务目录 `01_extraction` 写入。
- 项目二只向任务目录 `02_audit` 写入。
- 最终交付只读取真实报告，不重新计算审核结论。
- `complete_success`、`unverified`、`manual_review` 分别解释，不混为一谈。
