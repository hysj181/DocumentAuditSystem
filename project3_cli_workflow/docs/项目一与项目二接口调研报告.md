## 0. 结论摘要

1. 项目一和项目二都可以通过命令行独立运行，项目三适合用“独立子进程”方式整合，不需要导入两个项目的源码。
2. 项目一的标准交换文件是 `output/batches/<batch_id>/batch.json`，当前 `schema_version = "1.0"`。`output/json/<batch_id>.json` 内容与它同类，但批次目录下的 `batch.json` 是权威路径。
3. 项目一只接受 `.docx` 和 `.pdf` 文件，接受重复 `--input`，**不接受目录**。项目三必须自己展开目录、过滤扩展名。
4. 项目一默认输出到“项目一自己的 `output/`”，不是当前工作目录。项目三必须显式传入 `--output-root`。
5. 项目二通过 `--batch-json` 读取项目一批次，通过 `--output-dir` 指定输出根目录；会生成 `reports/` 和 `annotated/`。
6. 项目二不修改原始 Word/PDF，只写入新副本；项目一解析过程也不修改原始文件。
7. 项目二 `audit` 正常完成时退出码为 `0`，即使存在审核问题或人工核实项。不能只看退出码判断“审核完整成功”，必须读取报告中的 `metadata.pipeline.complete_success`、`stages`、`counts`、`warnings`。
8. 项目二 `validate-batch` 只做数学校验，且缺少统一异常处理；输入文件不存在时会输出 Python traceback 并返回 `1`。不建议在项目三主流程中与 `audit` 重复调用它。
9. 项目三需要自己实现：输入展开、运行目录、日志、阶段清单、幂等复用、最终交付目录。项目一和项目二本身不提供跨阶段工作流和断点恢复。
10. 当前真实样本批次可以完成审核，但该批次没有明确计算表达式，9 条环境记录全部为 `unverified`，0 个审核问题；这不表示“数据正确”，只表示“没有可验证的明确计算表达式”。

### 2.2 `extract` 子命令

```text
usage: main.py extract [-h] --input PATH [--mode {local_gpu,cloud_api}]
                       [--output-root DIR]
                       [--save-format {json,excel,markdown}] [--dpi DPI]
                       [--request-timeout REQUEST_TIMEOUT]
                       [--poll-timeout POLL_TIMEOUT] [--quiet]
```

| 参数 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- |
| `--input PATH` / `-i PATH` | 是 | 无 | 输入文件；可重复指定多个文件 |
| `--mode` | 否 | `local_gpu` | PDF 解析模式：`local_gpu` / `cloud_api` |
| `--output-root DIR` | 否 | 项目一自己的 `output/` | 输出根目录 |
| `--save-format` | 否 | `json` | 额外保存格式，可重复；`json` / `excel` / `markdown` |
| `--dpi` | 否 | `200` | PDF 渲染 DPI |
| `--request-timeout` | 否 | `300.0` | 云端 API 单次请求超时秒数 |
| `--poll-timeout` | 否 | `600.0` | 云端 API 轮询超时秒数 |
| `--quiet` | 否 | 关闭 | 不输出提取进度 |

实际行为：

- 无论 `--save-format` 选什么，都会保存 `batches/<batch_id>/batch.json`。
- `--save-format json` 会额外保存 `json/<batch_id>.json`。
- 重复执行不会覆盖已有文件，目标已存在时自动追加 `_1`、`_2`。
- 原始 Word/PDF 只读；导出逻辑会拒绝把导出路径设为原始文件路径。
- 支持一次传入多个文件，但**不支持目录**。传目录会被当作文件处理，最终得到“文件不存在”。
- 只支持 `.docx` 和 `.pdf`；旧版 `.doc` 不支持。

### 2.6 提取成功/失败判断

这是项目一最容易误判的地方。

退出码：

| 退出码 | 条件 |
| --- | --- |
| `0` | 至少一个文档成功 |
| `1` | 所有文档都失败 |
| `2` | 输入路径不存在或参数值错误等 `FileNotFoundError` / `ValueError` |
| 其他 | 未捕获异常 |

代码依据：

- `cli.py::_handle_extract` 最后执行：
  `return 0 if any(document.succeeded for document in batch.documents) else 1`
- `_handle_extract` 会先保存批次，再返回退出码。
- `DocumentResult.succeeded` 的判断是 `error is None`。

因此必须同时检查：

```json
{
  "documents": [
    {
      "source_file": "...",
      "error": null,
      "warnings": []
    }
  ]
}
```

判断规则建议：

| 情况 | 项目三阶段状态 |
| --- | --- |
| 子进程退出码 `0`，且所有 `documents[].error == null` | `succeeded` |
| 子进程退出码 `0`，但存在 `documents[].error` | `partial` |
| 子进程退出码 `1`，批次文件仍存在，全部文档有错误 | `failed` |
| 子进程退出码 `2` | `input_error` |
| 找不到 `batch.json` 或 JSON 无效 | `failed` |
| 存在 `warnings` 但没有 `error` | 仍可继续，但必须记录警告 |

特别注意：项目一即使全部文档失败，也可能已经生成了 `batch.json`。所以“退出码非 0”不等于“没有批次文件”，项目三应先检查批次文件，再决定是否分类失败。

### 2.7 是否支持一次处理多个文件

支持。调用方式：

```powershell
--input file1.docx --input file2.pdf
```

不支持：

- 直接传文件夹。
- 通配符自动展开（例如 `--input "D:\data\*.docx"` 不能依赖 shell 展开，项目三应自己展开）。
- 旧版 `.doc`。
- 真正的增量提取或单文档续跑。

项目一内部是逐文件循环，单个文件异常会写入该文档的 `error`，不会中断整批。环境数据提取阶段会跳过带 `error` 的文档。

### 2.8 是否修改原始文件

不修改。项目一只读取 Word/PDF；写出只发生在 JSON、Markdown、Excel 和批次文件。导出代码还有 `_guard_original_files`，阻止导出路径与原始文件相同。

### 3.3 `audit` 子命令

```text
usage: word-audit audit [-h] --batch-json BATCH_JSON [--output-dir OUTPUT_DIR]
```

| 参数 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- |
| `--batch-json` | 是 | 无 | 项目一批次 JSON 路径 |
| `--output-dir` | 否 | `output` | 输出根目录；报告写入 `<output-dir>/reports`，批注文件写入 `<output-dir>/annotated` |

完整流程：

```text
读取批次 JSON
  -> 输入结构校验
  -> 数学校验
  -> 错别字检查
  -> 收集审核问题
  -> 定位 Word/PDF 位置
  -> Word 红色文字批注 / PDF 红色矩形标记
  -> 生成数学、批注、完整审核报告
```

退出码：

| 退出码 | 条件 |
| --- | --- |
| `0` | 流程正常完成，即使存在审核问题或人工核实项 |
| `2` | 批次 JSON 不存在、JSON 结构无效、`environmental` 缺失、`documents` 为空、`file_type` 无效等输入错误 |
| `1` | 文件读写错误或其他运行错误 |

实际测试：

- 对真实批次运行 `audit`：退出码 `0`，`complete_success = True`。
- 对不存在的批次运行 `audit`：退出码 `2`，stderr 输出明确错误。

### 3.7 审核成功/失败判断

必须区分三层概念。

**第一层：进程是否成功执行**

- 退出码 `0`：审核流程执行完成。
- 退出码 `2`：输入结构错误，没有可信审核结果。
- 退出码 `1`：运行错误。

**第二层：审计流程是否完整完成**

读取 `audit_report_<batch_id>.json`：

```text
metadata.pipeline.complete_success
```

真实代码中，`complete_success = true` 需要同时满足：

- 没有源文件缺失警告；
- 所有问题定位状态都是 `located`；
- 没有批注失败；
- 没有批注阶段人工核实项。

注意：

- `unverified_count > 0` 不会导致 `complete_success = false`。
- `issue_count = 0` 不代表数据一定正确，只代表没有触发当前规则的问题。
- 低置信度错别字、无法定位、源文件缺失都会让 `complete_success = false`，但进程仍然返回 `0`。

**第三层：审核发现了什么**

读取：

```text
summary
metadata.pipeline.counts
metadata.pipeline.typo_counts
metadata.pipeline.stages
metadata.pipeline.warnings
metadata.pipeline.errors
```

建议项目三使用以下状态：

| 条件 | 项目三阶段状态 |
| --- | --- |
| 退出码 `0`，审计报告存在，`complete_success = true` | `succeeded` |
| 退出码 `0`，审计报告存在，`complete_success = false` | `partial`（审核完成，但有人工核实/定位/批注不完整） |
| 退出码 `2` | `input_error` |
| 退出码 `1` 或报告缺失/无法解析 | `failed` |

**绝不能**把 `complete_success = false` 说成“审核失败”，也**绝不能**把 `complete_success = true` 说成“数据合规”。它只表示项目二流程完整、未留下待人工处理项。

### 3.8 项目二是否修改原始 Word/PDF

不修改。

代码依据：

- Word：`word_annotator.py` 读取原文件后，通过 `document.save(output_path)` 保存到 `<output-dir>/annotated/<原名>_annotated.docx`。
- PDF：`pdf_annotator.py` 打开原文件，在内存页面上画红色矩形，再 `pdf.save(output_path)` 保存到 `<output-dir>/annotated/<原名>_annotated.pdf`。
- 输出文件名冲突时使用 `unique_path` 增加 `_1`、`_2`。
- 项目二文档和代码均声明原始文件只读。

项目二会读取原始文件来重新核对定位和写入副本，因此原始文件必须仍然存在于项目一 `source_file` 记录的绝对路径上。移动或删除原文件会导致定位/批注进入人工核实或失败。

## 5. 项目三整合方案

### 5.1 总体原则

1. **独立调用**：项目三只通过子进程调用项目一和项目二，不导入、不修改、不复制两个项目的业务代码。
2. **显式路径**：所有输入、输出、项目根目录、Python 解释器均使用绝对路径。
3. **不覆盖**：最终交付目录使用新建运行目录；项目一、项目二自身已有“唯一文件名”机制，项目三不覆盖旧结果。
4. **不伪造**：项目三只做编排、采集、汇总和复制，不生成、不修改审核结论。
5. **可恢复**：通过运行清单记录阶段状态和产物哈希，重复运行只复用已成功阶段。
6. **可解释失败**：每个阶段记录命令、退出码、stdout/stderr、耗时、产物路径、错误类别。

### 5.2 完整调用流程

```text
用户输入
  ├── 单个文件 / 多个文件
  └── 输入文件夹（项目三展开）
        |
        v
[0] 输入解析
  - 规范化为绝对路径
  - 去重
  - 过滤 .docx / .pdf
  - 记录不支持的文件
        |
        v
[1] 创建运行目录 + 运行清单
  - 计算输入指纹
  - 判断已完成的阶段是否可复用
        |
        v
[2] 项目一提取
  <project1 python> <project1 main.py> extract
      --input <file1> --input <file2> ...
      --output-root <run>/01_extraction
      --save-format json
      --mode <local_gpu|cloud_api>
      --quiet
        |
        v
[3] 获取并校验 batch.json
  - 从 <run>/01_extraction/batches/*/batch.json 读取
  - 校验 schema_version == "1.0"
  - 校验 documents 数量
  - 检查 documents[].error
        |
        v
[4] 项目二审核
  <project2 python> <project2 main.py> audit
      --batch-json <batch.json>
      --output-dir <run>/02_audit
        |
        v
[5] 校验审核产物
  - 读取 <run>/02_audit/reports/audit_report_<batch_id>.json
  - 读取 metadata.pipeline
  - 记录 complete_success / counts / warnings
  - 不生成、不修改任何审核结论
        |
        v
[6] 导出交付结果
  - 复制 audit_report JSON/Markdown
  - 复制 annotation_report JSON/Markdown
  - 复制 math_validation JSON
  - 复制 annotated/ 下的批注文件
  - 生成运行摘要（只汇总真实产物）
        |
        v
[7] 输出最终结果目录 + 退出码
```

### 5.3 单文件、多文件、文件夹

项目三输入解析建议：

| 输入 | 处理 |
| --- | --- |
| 单个 `.docx` / `.pdf` | 直接作为 `--input` |
| 多个文件参数 | 全部传给同一次项目一提取，保持同一批次 |
| 输入文件夹 | 默认只扫描当前层 `.docx` / `.pdf`；可选 `--recursive` 递归 |
| 文件夹中的 `.doc` | 跳过并记录警告；不静默改名 |
| 文件夹中的其他文件 | 跳过并记录警告 |
| 重复路径 | 按 `resolve()` 后去重 |
| 无任何支持文件 | 输入错误，退出码 `2`，不调用项目一 |
| 逗号分隔或列表文件 | 可选扩展，不作为第一阶段必需 |

排序建议：按规范化绝对路径排序，保证相同输入产生相同运行指纹。

多文件放入同一批次的好处：

- 保留项目一的企业归并能力；
- 项目二一次审核可覆盖全部文档；
- 报告只有一个 `batch_id`，交付关系清晰。

限制：

- 项目一不支持增量提取。新增一个文件会使整个输入集合指纹变化，需要重新提取整批。
- 项目二不支持按文档增量审核。批次 JSON 变化后需要重新审核整批。
- 项目三不能通过合并旧 JSON 来“拼”新批次，否则会伪造项目一结果。

阶段状态建议：

```text
pending
running
succeeded
partial
failed
input_error
reused
skipped
```

退出码建议：

| 退出码 | 含义 |
| --- | --- |
| `0` | 全流程完成，交付已生成，`complete_success = true` |
| `2` | 用户输入错误（无文件、不支持、路径不存在、参数冲突） |
| `3` | 已生成部分交付，但存在文档提取失败、人工核实、定位/批注不完整 |
| `4` | 阶段失败（项目一失败、项目二输入错误、报告缺失、复制失败） |
| `5` | 内部错误（清单损坏、未知异常） |

注意：项目二 `complete_success = false` 时项目三应返回 `3` 或明确标记“部分完成”，不能返回 `0` 假装完整成功。

### 5.7 不重复执行已完成阶段

建议算法：

1. 规范化输入，计算每个文件的 SHA-256、大小、修改时间。
2. 生成 `job_key`，包含输入集合、项目路径、模式等。
3. 读取 `<output-root>/<job_key>/manifest.json`。
4. 检查 `extract`：
   - 状态 `succeeded`；
   - `batch.json` 存在；
   - `batch_sha256` 与当前文件一致；
   - `schema_version == "1.0"`；
   - 输入指纹一致；
   - 满足则标记 `reused`，不调用项目一。
5. 检查 `audit`：
   - 状态 `succeeded`；
   - 审计报告存在且可解析；
   - 报告中的 `source_batch` 指向当前批次；
   - 当前批次哈希与清单记录一致；
   - 满足则标记 `reused`，不调用项目二。
6. 检查 `delivery`：
   - 交付文件存在且大小/哈希与清单一致；
   - 满足则直接输出结果目录。
7. 任何前置输入变化，使相关阶段及其后续阶段失效，重新执行。
8. 若项目一状态为 `partial`：
   - 默认不自动重跑，避免重复消耗 PDF/OCR 时间；
   - 明确标记 `partial`；
   - 继续项目二审核成功文档，最终交付标注失败文档；
   - 提供 `--retry-extraction` 让用户显式整批重跑（项目一不支持单文档续跑）。
9. 若项目二状态为 `partial`：
   - 不自动重跑；
   - 交付仍生成；
   - 运行摘要列出人工核实/批注失败/定位失败；
   - 提供 `--retry-audit` 显式重跑。

绝不能通过“看输出目录里有没有文件”来决定复用，必须校验 `batch_id`、`source_batch` 和 SHA-256，避免把旧批次报告当成本次结果。

### 5.8 日志

建议 `04_logs/run.log` 使用 UTF-8 文本，逐行记录：

```text
[2026-11-01T08:00:00+08:00] INFO  stage=extract start
[2026-11-01T08:00:00+08:00] INFO  command=...
[2026-11-01T08:02:10+08:00] INFO  stage=extract exit_code=0 duration=130.0s
[2026-11-01T08:02:10+08:00] WARN  documents=2 succeeded=1 failed=1
[2026-11-01T08:02:11+08:00] INFO  batch_json=...
[2026-11-01T08:02:11+08:00] INFO  stage=audit start
...
```

要求：

- 同时捕获 stdout 和 stderr，保留原始文本。
- 子进程环境设置 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`，并使用 `errors="replace"` 兜底。
- 不记录 `PADDLEOCR_ACCESS_TOKEN`。
- 不记录完整 Word/PDF 内容。
- 命令日志中的路径可以记录，但敏感信息需过滤。
- 失败时保存 stderr 末尾若干行到 manifest 和运行摘要，便于快速定位。

## 6. 可能遇到的接口兼容问题

### 6.1 项目一相关

| 编号 | 问题 | 影响 | 项目三应对 |
| --- | --- | --- | --- |
| P1-01 | 默认输出根目录是项目一自己的 `output/`，不是调用者当前目录 | 结果写到错误位置 | 始终显式传 `--output-root` |
| P1-02 | 不支持目录输入 | 文件夹输入会把目录当文件 | 项目三展开目录并过滤扩展名 |
| P1-03 | 不支持 `.doc` | 旧 Word 文件失败 | 明确提示不支持，不自动改名 |
| P1-04 | 退出码 `0` 可能包含部分失败文档 | 误判全部成功 | 检查每个 `documents[].error` |
| P1-05 | 退出码 `1` 时批次文件仍可能存在 | 误判没有输出 | 先检查 `batch.json`，再读错误 |
| P1-06 | 批次路径主要靠人类可读 stdout | 解析脆弱 | 独立输出目录 + 扫描 `batches/*/batch.json` + manifest |
| P1-07 | `table_count` 不含 Word 表格 | 统计错误 | 统计表格时同时扫描 `records[]` 中 `content_type="table"` |
| P1-08 | Word 表格无页码、无 bbox、无表头字段 | 不能按页/坐标定位 | 交给项目二处理；项目三不自行定位 |
| P1-09 | `source_location` 指向指标单元格，不是数值单元格 | 直接当数值列会定位错误 | 项目三不解释该字段；信任项目二定位 |
| P1-10 | `source_file` 是绝对路径 | 移动文件后项目二定位失败 | 项目三不移动原始文件；运行前校验存在性 |
| P1-11 | PDF 依赖 PaddleOCR，首次加载慢、内存高 | 超时被误判失败 | 设置足够超时；记录长耗时；不轻易重试 |
| P1-12 | 云端模式会上传 PDF，需要 Token | 隐私/网络风险 | 默认 `local_gpu`；云端必须显式开启并提示上传 |
| P1-13 | 无增量提取 | 新增文件需整批重跑 | manifest 明确标记，整批重跑，不拼接旧结果 |
| P1-14 | 多文件企业归并会影响环境记录归属 | 分批处理会改变结果 | 多个文件尽量放入同一批次，不随意拆批 |
| P1-15 | 中文路径/空格路径 | 拼接 shell 命令易失败 | 使用参数数组，不启用 `shell=True` |
| P1-16 | 输出编码/控制台编码差异 | 日志乱码 | 子进程设置 UTF-8 环境并兜底解码 |
| P1-17 | Word 默认 `extraction_engine="PaddleOCR"` | 误以为 Word 用了 OCR | 项目三不据此判断解析方式 |

### 6.2 项目二相关

| 编号 | 问题 | 影响 | 项目三应对 |
| --- | --- | --- | --- |
| P2-01 | `audit` 即使有问题也返回 `0` | 只看退出码会误判成功 | 读取 `metadata.pipeline.complete_success` |
| P2-02 | `complete_success=false` 不等于进程失败 | 误报阶段失败 | 标记 `partial`，交付仍生成 |
| P2-03 | `validate-batch` 无统一异常处理 | 输入错误输出 traceback，退出码 `1` | 主流程不调用；需要时统一捕获并解析 stderr |
| P2-04 | `validate-batch` 默认写入当前目录 `output/reports` | 污染项目三目录 | 显式传绝对 `--output` |
| P2-05 | `validate-batch` 与 `audit` 数学校验重复 | 重复执行、耗时 | 主流程只用 `audit` |
| P2-06 | 只接受 `schema_version="1.0"` | 未来版本不兼容 | 前置校验版本，失败时明确提示 |
| P2-07 | 要求 `environmental` 存在且为对象 | 旧批次可能不兼容 | 校验批次结构，不完整则停止 |
| P2-08 | 报告文件名固定，重复时自动加 `_1` | 难以仅凭文件名找最新 | 使用 manifest 记录精确路径 |
| P2-09 | 没有可批注问题时不会生成 `annotated/` | 误判批注失败 | 以 `output_files` 和 `annotations` 为准 |
| P2-10 | 源文件缺失不一定是输入错误 | 可能误判阶段失败 | 读 `warnings`、`stages.load`、定位状态 |
| P2-11 | PDF 旋转页、扫描页进入人工核实 | 批注不完整 | 标记 `partial`，列出人工核实项 |
| P2-12 | Word 批注是红色文字段落，不是原生批注 | 用户预期不一致 | 交付摘要中明确说明 |
| P2-13 | PDF 标记是红色矩形，不是文字批注 | 用户预期不一致 | 交付摘要中明确说明 |
| P2-14 | 输出目录相对路径依赖当前工作目录 | 输出跑到别处 | 始终传绝对 `--output-dir` |
| P2-15 | 一个命令只处理一个批次 | 多批次会混在一起 | 项目三按批次逐个调用 |
| P2-16 | 不提供增量审核 | 批次变化需整批重跑 | manifest 记录批次哈希，变化后整批重跑 |
| P2-17 | 不修改原始文件，但需要读取原文件 | 原文件移动会导致定位失败 | 运行前校验所有 `source_file` 存在 |
| P2-18 | 同名文件批注副本自动加 `_1` | 路径不稳定 | 从报告 `output_files` / manifest 取精确路径 |
| P2-19 | 低置信度错别字只进入人工核实 | `complete_success=false` | 作为正常审计结果展示，不伪造自动修复 |
| P2-20 | 报告中的 `unverified` 不是错误 | 误报“审核失败” | 单独展示 verified/unverified/issue |

### 6.3 跨项目问题

| 编号 | 问题 | 影响 | 项目三应对 |
| --- | --- | --- | --- |
| X-01 | 项目一和项目二都有独立 `.venv` | 用错解释器会缺依赖 | 分别使用各自 `.venv` 的 Python |
| X-02 | 两个项目默认输出位置不同 | 产物分散 | 统一放在项目三运行目录下 |
| X-03 | 项目二需要项目一原始文件仍然存在 | 复制/移动输入会破坏定位 | 直接使用原始绝对路径，不复制后删除 |

| X-05 | 两个项目都没有统一 JSON 错误码 | 难以自动分类 | 结合退出码、stderr、批次 JSON、审核报告综合判断 |
| X-06 | 中文字段和中文文件名 | 编码问题 | 统一 UTF-8；不改变文件名；参数数组调用 |
| X-07 | 项目二会把相对输出路径写到当前目录 | 交付路径混乱 | 项目三所有路径传绝对路径 |

- 测试输出写入临时目录或项目三运行目录。
- 退出码和 manifest 状态符合本报告定义。
- README 写明真实命令、限制和已知问题。

## 9. 最终推荐结论

项目三第一阶段之后，建议按以下优先级实现：

1. 先做“独立子进程 + 显式绝对路径 + manifest”骨架，不要直接导入项目一/项目二代码。
2. 先支持单文件和显式多文件，再支持文件夹展开。
3. 先使用项目一 `extract` 和项目二 `audit`，不要在主流程中额外调用 `validate-batch`。
4. 始终从项目二真实报告读取结果，不根据退出码或文件存在性猜测审核结论。
5. 始终校验原始文件存在，不移动、不覆盖原始 Word/PDF。
6. 所有结论保留来源路径，运行摘要只汇总真实产物。
7. 在真实样本上验证单 Word、单 PDF、多文件、部分失败和人工核实场景后，再扩展增量/恢复能力。

当前项目一和项目二已经具备可被项目三调用的稳定 CLI 契约；主要工作量不在审核算法，而在项目三的输入解析、阶段状态管理、错误分类、幂等复用和交付整理。
