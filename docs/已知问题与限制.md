# 已知问题与限制

- 记录日期：2026-11-01
- 适用基线：`V1.0.0`
- 说明：本轮只记录问题，不修复业务代码、依赖或模型。

## 1. PDF 当前使用 CPU 推理，速度较慢

- **现象**：PDF 使用 PaddleOCR PP-StructureV3 在本机 CPU 上推理；2 页 PDF 的正式混合任务整体耗时约 99.7 秒，其中大部分时间用于 PaddleOCR 模型初始化与 PDF 页面推理。
- **影响范围**：项目一 PDF 提取；项目三包含 PDF 的任务总耗时。
- **是否阻断主要流程**：否。真实 PDF 样本和完整回归测试均通过。
- **当前状态**：已接受当前 CPU 性能，本轮不继续优化。
- **后续建议**：如需提速，可在具备 CUDA 的机器上安装 GPU 版 PaddlePaddle 并重新验证；在此之前不要声称已启用 GPU 推理。

## 2. 当前 Paddle CUDA 不可用

- **现象**：实际检查结果为 `is_compiled_with_cuda()=False`、`cuda.device_count()=0`、`get_device()=cpu`。
- **影响范围**：PDF 本地推理性能；GPU 推理能力验证。
- **是否阻断主要流程**：否。CPU 推理可完成当前样本解析。
- **当前状态**：当前环境没有可用 CUDA，未验证真实 GPU 推理。
- **后续建议**：在具备 NVIDIA GPU 和 CUDA 的环境中单独验证 GPU 版 PaddlePaddle；不要把 `local_gpu` 模式标签当作 GPU 已启用。

## 3. `local_gpu` 名称与实际 CPU 设备容易误解

- **现象**：项目一、项目三使用 `local_gpu` 表示“本地 PaddleOCR 推理模式”，但当前实际设备是 CPU。
- **影响范围**：运行模式阅读；验收结论表述；用户对性能的预期。
- **是否阻断主要流程**：否。项目一 PDF 元数据已记录 `local_device.device=cpu` 和“GPU 不可用：当前为 Paddle CPU 版”。
- **当前状态**：代码和文档已明确说明该标签不代表实际 GPU 推理；本轮未重命名模式，避免破坏兼容性。
- **后续建议**：报告和交付说明中同时写明“模式=local_gpu、实际设备=cpu”；如未来重命名，应保留旧模式别名。

## 4. 偶发 `WinError 5` 交付目录重命名失败

- **现象**：隔离的部分成功故障注入任务第一次运行时，项目三在把 `.03_delivery_staging` 重命名为 `03_delivery` 时出现 `[WinError 5] 拒绝访问`；该次任务整体标记为 `failed`，提取和审核结果保留。
- **影响范围**：项目三交付阶段；部分成功任务的首次运行。
- **是否阻断主要流程**：否。对同一任务执行 `resume` 后交付成功，整体状态变为 `partial`；使用全新输出根目录重跑同一输入也一次成功。正式成功任务和补充批注任务未复现。
- **当前状态**：未稳定复现，判断为 Windows 文件句柄/安全扫描导致的瞬态失败；`resume` 可恢复。本轮未修改业务代码。
- **后续建议**：后续可评估交付目录重命名失败的重试机制或更稳健的原子替换策略；在此之前，遇到退出码 5 且交付目录缺失时先执行 `resume`，不要删除任务目录。

## 5. 文档部分内容尚未同步

- **现象**：项目三历史测试报告和早期文档中仍保留“PDF 本地提取失败”“21 failed”“尚未解决”等旧表述；项目一旧文档也记录过 PaddlePaddle 3.2.0。
- **影响范围**：文档阅读和版本判断。
- **是否阻断主要流程**：否。当前代码、测试和混合验收均已通过。
- **当前状态**：本轮已同步项目一 README、项目三 README、项目三用户使用手册和项目三测试报告的关键状态，并在历史报告顶部增加状态说明；历史记录仍保留。
- **后续建议**：以根目录 `README.md`、`docs/版本与环境清单.md`、`docs/测试与验收总报告.md` 为准；旧报告仅作历史参考。

## 6. `input_manifest` 状态仍可能保持 `pending`

- **现象**：正式任务提取成功后，`00_inputs/input_manifest.json` 中每个输入的 `status` 仍为 `pending`。
- **影响范围**：输入清单阅读；按输入状态判断成功的自动化消费方。
- **是否阻断主要流程**：否。`manifest.json` 的 `extraction_status`、`batch.json` 的 `documents[].error` 和批次统计是权威状态。
- **当前状态**：未修改项目三业务代码；已在使用手册和总报告中说明。
- **后续建议**：后续版本可考虑在提取完成后回写每个输入的状态；当前消费方应读取 `manifest.json` 和 `batch.json`。

## 7. Word 表格序列化存在不完整情况

- **现象**：Word 文档中的表格值已进入环境数据记录（含 `table_index/row_index/column_index`），`documents[].metadata.table_count=1`，但 `documents[].table_count=0`，文档级 `tables=[]`；`batch.json` 顶层 `tables` 只包含 PDF 表格。
- **影响范围**：仅依赖 `tables` 字段的消费方；直接读取 Word 表格结构化数据的场景。
- **是否阻断主要流程**：否。项目二审核所需的环境数据记录包含 Word 表格值；与历史真实批次行为一致，不是本轮回归。
- **当前状态**：未修改项目一业务代码；已在验收报告和总报告中记录。
- **后续建议**：后续版本可评估将 Word 表格完整写入文档级 `tables`，同时保持 `schema_version` 兼容。

## 8. 项目二审核能力目前以规则和词典为主

- **现象**：项目二当前实现数学表达式校验、保守错别字词典、定位和批注，不包含完整语义理解、合规判断、单位错误、数据缺失等规则。
- **影响范围**：审核覆盖面；用户对“智能审核”的预期。
- **是否阻断主要流程**：否。当前规则审核已通过 125 项测试，并在混合验收中正常运行。
- **当前状态**：文档已明确说明“不是完整 AI 智能审核系统”。
- **后续建议**：不要宣传为完整 AI 审核；如需扩展，应新增明确规则、测试和可解释依据。

## 9. 正式样本 21 条均未验证，不能据此认定所有业务规则已验证

- **现象**：正式混合任务的 21 条环境数据全部为 `unverified`，`issue_count=0`。这表示没有可验证的明确计算表达式，未发现可确认问题。
- **影响范围**：审核结论覆盖范围；业务规则有效性判断。
- **是否阻断主要流程**：否。数据提取、审核流程和交付均成功。
- **当前状态**：未人为制造问题，未伪造批注；补充错别字样本单独验证了定位和批注链路。
- **后续建议**：补充包含明确计算表达式和已知错别字的真实业务样本，才能验证更多审核规则；不要把“未验证”描述为“审核通过”。

## 10. 复制整个任务目录后阶段复用失效

- **现象**：把任务目录复制到新的输出根后执行 `resume`，manifest 中的 `batch_json_path` 仍是原任务绝对路径，项目三判定批次不属于当前任务目录，因而重新执行提取、审核和交付。
- **影响范围**：任务目录迁移、备份副本恢复。
- **是否阻断主要流程**：否。`resume` 最终成功；正式任务和交付阶段恢复不受影响。
- **当前状态**：未修改项目三业务代码；已记录该行为。
- **后续建议**：迁移任务目录时保留原绝对路径，或在后续版本中支持可配置的任务目录重定位；不要直接复制后假设阶段一定复用。

## 11. Word 批注不是原生审阅批注

- **现象**：项目二在 Word 原文段落之后或表格单元格内写入红色文字段落，不是 Word 原生批注/修订记录。
- **影响范围**：Word 批注阅读方式；用户对“批注”的预期。
- **是否阻断主要流程**：否。红色文字批注可定位、可查看、可交付。
- **当前状态**：项目二 README 和 pipeline 文档已明确说明。
- **后续建议**：如未来需要原生 Word 批注，应单独设计并验证，不要在当前文档中宣称已实现。

## 12. 未实现 GUI、Web、分布式锁和首次并发全局去重

- **现象**：项目三只提供 CLI；任务锁为单机文件锁；两个进程同时首次运行相同输入且尚无任务时，可能各自创建任务。
- **影响范围**：界面使用、跨机器并发、首次并发去重。
- **是否阻断主要流程**：否。单机顺序运行和复用已验证。
- **当前状态**：未开发，本轮不开发新功能。
- **后续建议**：如有多机/并发需求，应单独设计分布式锁和全局去重，不在当前版本中宣称支持。
